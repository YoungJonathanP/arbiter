# 0.4.16: personal input controls and connected work

Repository candidate, 2026-09-12. Protocol and base schema advance to 0.4.16;
the new person schema is 0.4.16. Existing concrete schema versions are unchanged.
This continues [0.4.15](v0.4.15-input-storage.md) and the agreed
[app direction](user-app-direction.md). No installed KB adoption is implied.

## Implemented behavior

The shared task app supports structured status changes, Done/checklist resolution,
Undo, quick notes, linking existing notes/meetings, appointment capture and editing,
creating or connecting person/entity cards, disconnecting relationships and
attributed incorporation. Existing task body editing remains an agent operation;
the incorporation control authors an appended addition with source attribution.
Preview returns exact before/after bytes. The server retains the preview under a
random, single-use ID bound to actor/task for 15 minutes (32 retained previews per
API instance). Apply ignores request-authored replacements and rechecks the input
basis, source revisions, access and receipt sequence through the stored writer.

Appointments use existing meeting schemas, with a required calendar date and a
separate descriptive time/timezone field in prose. Corrections retain old prose,
anchors, identity and link incarnation, append a dated revision, and update the
structured title/date/touch metadata. A changed source revision becomes actionable
again even after dismissal. Read existing appointment loads exact source bytes
before editing. Scheduling does not change task status or send calendar events.

`people/<id>.md` is a stable person/entity record. Its `date` is capture date;
Summary holds context. It does not represent an authenticated account. Task and
person views use the same audience-filtered ledger edges. Even an `owner` edge
does not assign the task's canonical owner. Creating a card sends nothing.

The compact dashboard remains five entries per card. `/active` provides the
complete nonarchived, nonterminal goal/task set, including nested and old active
work, with 20 rows per page and an equivalent JSON view. It displays current
checkpoint summaries and actionable shared-input counts; unreadable or malformed
review state is explicitly unresolved. `/personal/active` lists the authenticated
principal's accessible active work with the same membership and paging rule.
This reconciles full active-work discovery with a bounded dashboard and separate
handoff budgets; it does not change historical item bytes.

## Trusted local personal access

`arbiter serve --data <kb> --personal-policy <outside-kb.json>` enables an opt-in
local personal surface at `/personal/tasks/<id>`, `/personal/people/<id>` and
`/personal/active`. The CLI requires a loopback bind and a policy outside the KB.
A host embedding the server supplies the same trusted adapter explicitly.
Ordinary pages/API remain the shared local-operator surface and conservative
exports. This is local principal authentication, not remote hosting or SSO.

The policy is an owner-owned regular JSON file with mode 0600. Shape:

```json
{
  "version": 1,
  "principals": { "alice": { "tokenSha256": "<64 lowercase hex digits>" } },
  "readers": { "journal/example.md": ["alice"] },
  "inherit": { "journal/second.md": "journal/example.md" }
}
```

Use hashes of random tokens at least 32 characters long, not human passwords.
The browser's HTTP Basic challenge takes the principal ID and its token on
loopback. Tokens are never stored in a KB, URL, page or returned JSON. POSTs also
require the per-process token, loopback Host/peer and same-origin check. The JSON
body cannot select a principal or grant access. Existing explicit grants and
inheritance are local administrator decisions, using filesystem review and CAS;
there is no browser grant-administration endpoint. Cycles, ambiguous rules,
unknown principals, invalid configuration and permissive file modes fail closed.
Policy changes invalidate input bases and retained previews. Filesystem access
remains privileged and outside this app authorization boundary.

`readers` keys name exact canonical paths or exact ledger edge keys
`tasks/<id>/input-review.md#<edge-UUID>`. An inherited grant must be declared by the
trusted administrator. An unresolved inherited grant denies access. Edge grants
are independent of endpoint grants; private metadata without a rule denies access.
Canonically shared records always remain shared, even if a personal policy entry
names fewer readers; otherwise private incorporation could leak through default
exports. To change canonical visibility requires a separate explicit action. A card identity
never becomes an authenticated account implicitly.

Personal controls capture new notes, appointments and cards as private to the
current principal. Trusted provisioning reserves fresh generated source/entity
and edge IDs for that principal only; it never grants access to an existing
record. Existing endpoint connections require readable endpoints and create a
new principal-only edge. Provisioning uses a cooperating lock/CAS, retains exact
old policy bytes in an owner-only sibling history file, replaces and rereads the
policy, then writes content/intent through the KB's existing commit path.
Interrupted sequences may leave reserved grants for absent generated resources;
these confer no access to an existing record. Reconcile policy and KB state
explicitly; never restore either file over concurrent edits. This is not one atomic
transaction spanning the host policy, task, ledger and source files.

Personal Done/Undo uses the same explicit human exception and staging/checklist
checks. Private notes on a shared task can be reviewed/presented privately but
cannot be incorporated into shared prose: both source and link audiences must
cover the destination's readers. Permission checks do not detect sensitive prose.

## Storage extension and compatibility

The byte-stable ledger header/pointer retain storage format 0.4.15. Under protocol
0.4.16 only, intent effects additionally support `source-edit` with a source ref
and `relationship` creation of a person card. Source edits require an existing
linked source and non-null, changed before/after bytes at that source. Person
creation requires a null before at exactly its `people/<id>.md` endpoint. Applied
completion is required; neither effect acknowledges source input. Old ledgers
remain byte-identical. Protocol 0.4.15 refuses these extended operations.

## Remaining adoption gates

The local controls have synthetic HTTP tests; no browser automation, installed
live behavior or fresh-agent measurement is claimed. The
[0.4.17 continuation candidate](v0.4.17-personal-continuation.md) now binds
personal authentication, exact private revisions, receipts and the complete packet
budget. Its supported scope is private input alongside a shared canonical
checkpoint; restricted checkpoint dependencies fail closed. Default packets remain
shared-only. Check selected-target compatibility and imported-record preflight
before adoption; synthetic client tests do not establish fresh-agent acceptance.

Reconcile the exact installed 0.4.7 contract with the full 0.4.16 candidate while
preserving applicable user directives, item prose/history and existing refs/anchors.
Then, on the selected independent evaluation copy only, verify backups, allocate a
fresh UUID, migrate and measure capture/export/rollback. The historical seven-file
bundle remains insufficient. Fresh-session agent execution is a separate,
still-unauthorized gate. Live rollout and live reconciliation remain separate.
