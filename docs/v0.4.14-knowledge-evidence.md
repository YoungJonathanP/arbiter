# v0.4.14: Durable knowledge and recorded impact

T08 adds decisions and findings that remain discoverable after their source task
closes, editable accomplishment candidates, and date-ranged Markdown reports.
Protocol/base and accomplishment/decision/finding schemas advance to 0.4.14;
task/goal/meeting/journal remain 0.4. Legacy protocol 0.4.6/8/9/10/11/12/13 and
accomplishment 0.4 remain accepted. No installed contract is upgraded by these tools.

## Decisions

1. **One supported type catalog, bounded extensibility.** `ITEM_TYPES` in
   `src/core/model.ts` owns type, directory, label, kind, version and introduction.
   Corpus enumeration, facts, schema compatibility, CLI directory checks, creation,
   dashboard and web routes derive registration from it. Schemas still define
   fields and sections. The earlier promise that adding a schema file alone enables
   a card was false and is withdrawn. A supported addition needs one catalog entry
   and its schema; arbitrary schema plugins remain unsupported. Legacy dashboards
   retain their existing empty-card layout; new knowledge appears when present or
   under the new protocol. The SQLite index includes source/supersession edges.
2. **Two durable knowledge types.** Decision records state a choice with scope and
   rationale; findings state reusable observations within a scope. Both carry date,
   source refs, Evidence, Observations, Uncertainty and review. New skeletons need
   review; reviewed records require reviewer/date, explicit scope and evidence.
   Supersession is an explicit acyclic object relation, available on every item.
   Older records keep their paths. Discovery and detail views show supersession,
   review and verification independently of execution status.
3. **Promotion prepares a claim for review.** Done status says work closed, not
   that its intended outcome occurred. Promotion therefore emits a candidate from
   the source's existing summary and visible artifacts, never fabricated numbers
   or observations. The caller supplies the outcome date and reviews the proposed
   identity before existing CAS capture. Evidence-less candidates are valid but
   unverified. The command does not mutate data or automatically create a record.
4. **Recorded attestation, explicit uncertainty.** `verification: observed` names
   the observer and observation date, the outcome identity, the actual observation,
   its evidence and remaining limits. Reports label these as recorded attestations;
   they never fetch URLs or claim independent verification. An external URL alone
   cannot move a candidate into counted impact. Human inspection still matters.
5. **Deduplicate outcomes, not activity.** Reports group all current eligible
   accomplishments by explicit outcome identity before applying the inclusive date
   range. Equal dates/claims count once and retain all source links. Conflicting
   claims/dates or unverified duplicates require review, including conflicts outside
   the requested date range. Related tasks and journals add no counts. Different
   identities for the same real outcome require authoring reconciliation; there is
   no semantic duplicate detector or inference from relationship graphs.
6. **Visibility precedes all report text.** Use `readProjection`, including archives
   and excluding history. Redacted source bytes are marked so incomplete provenance
   cannot silently qualify. Private/redacted records, missing provenance, non-done,
   dropped or superseded source work, unresolved source review/staging and superseded
   accomplishments are omitted. Local evidence must resolve to visible item/detail
   files and any named checklist anchor. Evidence owned by dropped/superseded work
   is unusable. No relationship bodies are copied recursively.

## Workflow

Use an explicitly selected, compatible KB. New KBs receive the new contract;
existing KBs require a separate, deliberate adoption decision.

```bash
arbiter new decision "Transport selection" --date 2026-09-08 --data /path/to/kb
arbiter new finding "Benchmark scope" --date 2026-09-08 --data /path/to/kb
arbiter search "transport" --dir decisions --archive include --data /path/to/kb
arbiter promote tasks/copper-2026q3 --date 2026-09-01 --data /path/to/kb > /tmp/candidate.md
```

Inspect `/tmp/candidate.md`. Its ID determines the destination. Reconcile the
proposed `outcome` with existing accomplishments, preserve `source`, and supply
actual observations, evidence and limits. Keep verification unverified until the
observation has actually been made. Then capture using the existing write contract:

```bash
arbiter write accomplishments/copper-impact-2026q3.md --if-match new --file /tmp/candidate.md --data /path/to/kb
arbiter validate --data /path/to/kb
arbiter report --since 2026-09-01 --until 2026-09-30 --data /path/to/kb
```

`--until` defaults to the caller's current day; `--now` sets deterministic capture/
generation time. Date filters select outcome dates rather than update/archive dates.
Markdown source links are relative to the KB root: keep a saved report at that root
or resolve/rebase those links when exporting elsewhere. Reports write stdout only.

## Verification and limits

`test/evidence.test.ts` starts with one archived copper workstream and its benchmark
record: two accomplishments with the same outcome yield one counted outcome, both
record links, the archived source, the measurement link and unresolved production
tail latency. It also covers candidate capture, empty evidence, date errors,
contradictory duplicates, private evidence/source records, supersession, dropped and
review/staged work, schema capture/query/cards/web rendering and reviewed knowledge.
The generated [synthetic report](examples/impact/REPORT.md) provides a reviewable
example with source files; its numbers are fictional test data.

Reports scan current files and do not provide an atomic snapshot or external-editor
guarantee. Known-token privacy redaction cannot detect paraphrased private facts.
Malformed/raw records or missing outcome dates/provenance cannot be placed in a
dated report; whole-KB validation diagnoses source structure separately. A report
can become stale after source edits and should be regenerated. No report GUI,
network verification, timeline, custom schema plugin loading or installed-KB
migration is included. See [completion evidence](handoffs/completed/t08.md).
