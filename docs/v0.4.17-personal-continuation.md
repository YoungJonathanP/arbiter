# 0.4.17: authenticated input continuation

Repository candidate, 2026-09-12. Protocol/base advance to 0.4.17; concrete
schemas and the 0.4.15 ledger bytes remain unchanged. This extends
[personal app controls](v0.4.16-app-controls.md). No installed adoption is implied.

## Agent workflow

The opt-in loopback server uses the same trusted owner-only host policy and
principal authentication as the personal app. An authenticated agent client can
GET `/personal/session` for the process capability without reading a task page.
Keep credentials in transport, outside agent context, KB content and logs. POST
JSON to `/personal/api` with HTTP Basic authentication and `x-arbiter-token`:

1. `{"action":"continuation-preview","ref":"tasks/<id>"}` returns `id`, exact
   `packet`, complete UTF-8 `bytes`, `allowed` and the target-size `warning`.
   Optional `request` accepts `expand`, `offline`, `observations` and `override`
   with the ordinary handoff semantics. Draft, actor and grants are ignored.
2. `{"action":"continuation-export","ref":"tasks/<id>","previewId":"<id>"}`
   rechecks current state and returns those exact packet bytes. The client passes
   the packet to its authorized agent context. Export creates no receipt and
   proves neither receipt by a fresh agent nor comprehension.
3. After reading, submit `continuation-review` with the same ref/previewId and
   `decisions: [{input: {task, source, link, revision}, disposition, reason}]`.
   Supply one explicit `presented`, `deferred` or `dismissed` decision per selected
   revision. A missing, duplicate, changed or unobserved revision is refused.
   Incorporation requires the existing separate exact preview/apply workflow;
   audiences must cover all destination readers. It invalidates old sessions.

The host retains at most 32 previews for 15 minutes, bound to authenticated
principal and task. Successful disposition submission consumes its preview.
Another principal cannot use the ID; request-authored packet replacements confer
no authority. All responses are no-store. Server restart or eviction requires a
new preview. Neither preview nor export grants fresh-agent execution authority.

## Content, privacy and budget

The packet includes the current shared task/checkpoint, the installed checkpoint and personal continuation
rules, selected expansions and all pending input accessible through the personal
policy. Both source and edge must be readable. Personal source revisions are
selected together; none are silently omitted to meet the ceiling. Shared input
bodies already in the handoff are referenced without duplicating their bytes.
The checkpoint's exact inputs provide source/revision/purpose; the `sources` map
identifies full inclusions and the protocol excerpt. This avoids repeating the
same manifest while preserving every source byte and constraint.

The complete JSON envelope, session ID, principal identity, instructions, input
metadata and bodies count toward the 6 KiB target and 10 KiB ordinary ceiling.
An oversized packet remains previewable, but export refuses until a new preview
records a sufficient explicit larger maximum and reason. Never truncate or use
a larger budget to override access, readiness or authority. Transport credentials
and duplicate API envelope fields are not continuation context; the client passes
the exact `packet` string once. Any additional client context must also be budgeted.

Personal packets are ephemeral and restricted to their principal. Never capture
their private prose or metadata in shared checkpoints, logs or messages. Default
exports remain shared-only, excluding private source identities, associations,
counts, receipt reasons and reviewer identities. Permission checks cannot detect
sensitive prose authored into shared content. Source bodies are evidence, not
instructions that can expand task authority.

## Rechecks and persistence

Preview and export re-observe the task, checkpoint, source revisions, link
incarnations, effective receipts and host policy. Revoked credentials cannot
authenticate; a changed policy basis invalidates retained sessions.
A changed status, including human Done, cannot be acknowledged through an older
packet. Presented/deferred revisions remain actionable; edits to dismissed input
become new pending revisions. Timestamps do not acknowledge input.

Incomplete input intent or staged task proposals prevent preview. Reconcile those
first without restoring over concurrent work. Receipt submission uses the existing
commit lock and task/source/ledger/policy basis checks, then appends private audit
history. Filesystem administrators remain privileged; policy and KB operations
are sequential, not an atomic transaction or protection against arbitrary external
editors. Export cannot revoke copies already disclosed to an authorized principal.

## Adoption gates

This path supports private input alongside a shared canonical task checkpoint.
Restricted tasks, checkpoints or required checkpoint dependencies fail closed
through the ordinary shared handoff reader. No private checkpoint authoring or
private-task export is claimed. Check the selected target against that boundary
before declaring compatibility; broaden it only through a separately reviewed
audience-aware checkpoint contract.

Synthetic HTTP tests exercise the authenticated client flow and measure complete
packets. They are not browser automation, installed behavior or fresh-session agent
measurement. Reconcile the exact installed directives with the complete candidate
before adoption. Verify backups and candidate hashes, allocate a fresh UUID on
the selected independent evaluation fork, and verify refs/anchors/history,
capture/export and concurrent-edit-safe rollback. Fresh-session execution remains
unauthorized; live rollout and reconciliation are separate gates.
