# v0.4.6 decisions — task nesting and tier-1 membership

*Decision record, 2026-07-10. Protocol 0.4.4 → 0.4.6 and grammar v0.4.5 → v0.4.6
(bumped together; the two specs are now version-synchronized). Directive: the
`_base` schema has always allowed `parent:` to name any item — including a task
parenting a task — but the presentation layers did not honor it. This change
makes nesting real: tier 1 shows only top-level work items; sub-items are
reached through their parent.*

## The rule

- **Sub-item**: a work item whose `parent:` resolves to an existing,
  non-archived item **in the same directory** (task under task, goal under
  goal). Everything else — no parent, parent in another directory (task under
  goal), parent unresolved, parent archived — is **top-level**.
- **Tier 1** work-item cards list only top-level items. Sub-items never appear
  on the dashboard; they are reached through their parent. The card header
  count excludes them.
- **Tier 2**: a parent's rendered view derives its child list from the
  children's `parent` refs — forward pointers are computed, never stored, like
  prev-chains. Each child appears as a summary entry (status dot, title,
  first summary line, -> link); opening it shows the child's own full view.
  In the files themselves nothing is added to the parent: agents reach
  children via `arbiter query children <ref>`, and a parent SHOULD carry a
  `see:` link to a load-bearing child from the checklist step it serves.

## Settled design points

1. **Staged flags roll up; nothing else does.** A tier-1 entry's
   `(<N> staged)` count is the sum of unresolved proposals across the item
   *and its sub-item descendants*. Rationale: the staged flag is the most
   urgent thing on a card and a session initializes from one dashboard read —
   hiding a sub-task must not hide its pending arbitration. Statuses do
   **not** roll up: `status:` is the item's own field, and a parent genuinely
   blocked on a child says so explicitly with a `[!]` step whose `blocked-by:`
   targets the child (existing grammar). A task under a goal contributes
   nothing to the goal's flag — that task is itself on the dashboard.
2. **Depth: one level supported, deeper flagged.** Membership and rollup are
   well-defined at any depth (the rules above are local), but the validator
   warns on a sub-item whose parent is itself a sub-item. Revisit if real
   corpora need more.
3. **Cycles are validator errors.** A `parent` cycle among same-directory
   items would make every member a sub-item — an unreachable island off
   tier 1 — so it fails validation. (Membership stays computable: the rule is
   local to one edge.)
4. **Unresolved or archived parent ⇒ top-level.** Losing a parent must never
   make a child invisible: a typo'd ref or an archived parent surfaces the
   child back on the dashboard (plus a validator error for the unresolved
   ref). Reachability is the invariant tier 1 must preserve.

## Gate impact

Gate 5 (index-is-cache) now states re-parenting explicitly: a `parent` change
that makes an item a sub-item is an **observed transition** that removes its
card entry, and one that makes it top-level restores the entry — in both
directions nothing is lost or duplicated by going unseen, and incremental
regeneration stays byte-identical to a full rebuild. The membership filter and
staged rollup run in card assembly, which both regen paths share, so the
guarantee is structural. The fixture corpus gains a nested sub-task (with its
own staged proposal) to lock membership, rollup, and the re-parenting
transition in the suite.
