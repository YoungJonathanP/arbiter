# 0.4.18: preserve legacy accomplishment claims

Repository candidate, 2026-09-12. Only the accomplishment schema advances to
0.4.18. Protocol/base stay 0.4.17; other concrete schemas and ledger bytes stay
unchanged. This refines the [evidence model](v0.4.14-knowledge-evidence.md) and
the [continuation adoption gates](v0.4.17-personal-continuation.md#adoption-gates).

## Compatibility

Installing schema 0.4.14 over the evaluation corpus produced 54 required-field
and section errors across 18 legacy accomplishments. Their existing claims and
Evidence links are historical records, not newly observed attestations. Rewriting
them to pass validation would mix schema migration with evidence authoring.

Schema 0.4.18 makes verification, Observations and Uncertainty optional for
unverified records. Absent verification means unverified, and validation emits an
advisory warning. It does not infer when a record was authored. Legacy-shaped
records still require their Evidence section and usable link under the existing
validation rule. Explicitly unverified candidates may have empty Evidence.

All observed-record requirements remain: stable outcome, eligible completed source,
observer, real observation date, nonempty Summary, Observations, Uncertainty and
Evidence. Reports independently require these and explicit observed verification;
missing metadata can never count as impact. Malformed verification values still
fail validation. Old installed schemas retain their own required-field behavior.

New skeletons and promotions explicitly emit unverified and both sections.
Validation, projection and reporting preserve source bytes, including historical
claims and line endings. No bulk normalization, invented observations, date
heuristics or certification manifests are part of adoption.

## Verification and adoption

Synthetic regression tests cover byte preservation, visible unverified claims,
complete metadata without explicit verification, invalid verification, observed
requirements, retained legacy Evidence requirements, older schema validation and
new candidate defaults. Real-corpus preflight is an in-memory overlay; it is not
installation, migration or fresh-agent measurement.

Reconcile the exact candidate and selected target's privacy, refs/anchors and
proposal/scope conflicts before adopting an independent fork. Preserve all source
bytes and verified backups; allocate a fresh UUID only when those gates pass.
Restricted checkpoint dependencies still fail closed. Live rollout and fresh-agent
execution remain separate from this compatibility change.
