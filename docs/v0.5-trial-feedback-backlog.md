maps all 17 items to independent task packets and adds the architecture review's

and verified; a written plan does not close them.

**Standing observation:** three of the four highest-severity items
(`cas-digest-prefix`, `arbitrate-false-applied`, `arbitrate-backdated-updated`)
sit on the arbitration/CAS path. That machinery carries the protocol's central
"silent loss is structurally impossible" claim and is the least exercised code in
the CLI, because single-writer sessions never reach it. Treat it as one work
package, not three tickets.

## Correctness — arbitration and CAS

### 1. `arbiter write --if-match` rejects the digest `arbiter hash` prints
`^cas-digest-prefix`

`arbiter hash` prints `sha256:<digest>`; `--if-match` accepts only the bare
digest. The copy-paste the arbiter skill prescribes fails on first use. The error
message reports a "CAS mismatch" and prints a digest identical to the one passed,
minus the prefix it never mentions, then advises "re-read, rebase or stage a
proposal". An agent that follows it manufactures contention over a string bug.

1. Accept both forms. Strip an optional `sha256:` prefix before comparison.
2. Report a prefix-only difference as a **format** error, not a mismatch. Keep the
   rebase-or-stage advice for real contention.
3. On a real mismatch, print expected and actual as two labelled values.

### 2. `arbiter arbitrate` reports an `append:` op applied when it drops it
`^arbitrate-false-applied`

Observed 2026-08-05. Two pure appends were staged. `append: Summary · …` landed.
`append: Detail docs · …` was recorded `⇒ applied` and never written. The
proposal is deleted after arbitration, so the only surviving record asserts
success. This is exactly the silent loss the protocol claims is impossible.

Suspected cause, unverified: multi-word section targets. `Summary` is one word and
worked; `Detail docs` contains a space. Check whether the op parser or the section
locator splits on whitespace, and whether an unmatched section falls through to a
no-op instead of an error.

1. An op that cannot be applied must never report `applied`. Apply it, or record
   `⇒ overruled (<reason>)`.
2. Verify appends post-write. Re-read the item and confirm each `append:` op's
   text is present before the proposal is deleted.
3. Fix multi-word section targets. Add regression tests for `Detail docs`,
   `Artifacts`, and `Evidence`.
4. Consider a refusal to delete a proposal whose ops did not verify.

### 3. `arbitrate` backdates `updated:` and strands marks across views
`^arbitrate-backdated-updated`

Observed 2026-07-28. A card read `[todo]` while the item file read `status: done`,
and stayed wrong across regens. `arbitrate` applied `set: status = done` but
stamped the item's `updated:` from the proposal's staging time (10:00) instead of
the application time (~11:35). Incremental regen only folds in items newer than the
previous dashboard's `generated` (11:31), so the transition was invisible, and
permanently so.

1. `arbitrate` must stamp `updated:` with the application time. The proposal
   records when the change was requested; the item records when it changed.
2. Defense in depth: regen should correct a carried entry whose mark contradicts
   its item file, regardless of timestamps.

### 4. One malformed staged proposal turns `validate` red for every session
`^staged-blast-radius`

Observed 2026-07-28. A concurrent session staged a malformed proposal and global
`arbiter validate` went from 0 errors to 2. PROTOCOL forbids other writers from
editing a staged file they did not create, and the skill's session-end contract is
"finish green". One writer therefore makes that contract unsatisfiable for
everyone else, and arbitrating a stranger's in-flight proposal to get green is the
wrong incentive.

1. **Core ask.** Scope the blast radius. Global validate should downgrade another
   writer's malformed staged proposal to a warning or a per-item quarantine. Keep
   the hard error for `arbiter arbitrate` on that item.
2. Add an `arbiter propose <dir>/<id>` scaffold so this malformation class becomes
   impossible by construction. Staging is hand-rolled today.
3. Check the validator's item-ref expectation. The rejected
   `item: tasks/fnm-multishell-leak-2026q3` is the documented `<dir>/<id>` form;
   the validator compared it against the bare staged-dir id. If the validator is
   wrong, ask 2's error is a straight bug.

## Correctness — parsing and CLI arguments

### 5. One malformed `## Artifacts` line voids the whole section
`^artifact-line-recovery`

Observed 2026-08-10 on `tasks/empiricist-multi-repo-2026q3`. Two of 36 lines
carried a parenthetical **after** the closing paren of the link
(`- pr: [redfin-npm PR 1343](url) (MONEY-2135 library half, draft)`), outside the
`$` anchor of `LINK_ENTRY_RE` (`src/core/parse.ts:126`). `parseLinkEntries`
(`:129-138`) returns `null` for the whole section on the first non-match, so all 36
PR links dropped from the model and the renderer (`src/web/server.ts:719`) painted
an opaque `<pre>`. The validator (`src/core/validate.ts:205`) said only
`section "## Artifacts" is off-grammar`, so a reader cannot tell whether 1 line or
36 are at fault.

1. Recover per line. Skip and warn instead of voiding the section.
2. Name the offending **line number** and what was expected.
3. Apply the same shape to `parseDocsEntries` (`:140-149`) for `## Detail docs`.
4. Document the entry grammar in `PROTOCOL.md#capture`. The two sections diverge
   in a way that invites this mistake: `## Detail docs` puts its `(kind)`
   parenthetical **after** the link text, while `## Artifacts` requires any
   annotation **inside** the label. `#capture` currently shows no entry grammar at
   all, unlike `#tier-2`.

### 6. `arbiter new` needs `--date`, and unknown flags must not vanish
`^new-date-flag`

`arbiter new <type> <title...>` always stamps today into the slug and the `date:`
field. `PROTOCOL.md#slugs` defines a meeting slug as `<base>-YYYY-MM-DD` where the
date is the **meeting** date, and both normal capture moments (prep before, log
after) therefore mint a wrong id. Hit on 2026-08-05 creating a 2026-08-06 meeting.
Because ids are immutable addresses, the only recovery was to delete the stub and
hand-write the file, which skips the slug-form and reopen-rule enforcement that
`new` exists to provide.

1. Add `--date <YYYY-MM-DD>`. It drives the slug suffix, the `date:` field, and the
   quarter suffix. Future dates must be allowed.
2. **The more dangerous half.** Stop swallowing unknown flags. `--date` was neither
   honored nor rejected nor absorbed into `<title...>`. It vanished, and a wrong
   immutable id looked like success. Unknown flags must error with the usage
   string.
3. Same shape elsewhere: `arbiter validate <path> [<path>...]` ignores its path
   arguments and validates the whole directory, reporting another session's errors
   as the caller's own.
4. The subcommand usage line documents only `[--force]`, so no date option is
   discoverable to begin with.

### 7. `arbiter --help` launches the renderer instead of printing help
`^help-shows-cli-options`

Bare `arbiter` and any `--`-prefixed invocation are rewritten to `serve`
(`src/cli/main.ts`), so `--help` starts a server. `--help` and `-h` should print
the same text as `arbiter help` and exit.

### 17. A nonexistent data directory validates green
`^missing-data-dir` (found 2026-09-06 during handoff prep, not from the trial)

`arbiter validate --data /definitely/not/a/real/path` prints
`0 files, 0 error(s), 0 warning(s)` and exits 0. `arbiter regen` against the same
path renders a dashboard. Neither command distinguishes "the directory is empty"
from "the directory is not there."

This bites hardest on a **fresh machine**, which is the exact case where
`$ARBITER_DATA` points at a sibling directory that does not exist yet. The setup
looks correct, the session-end contract ("finish with validate green") is
satisfied by nothing at all, and no signal says the KB was never found.

1. Error when the resolved data directory does not exist. Name the resolved path
   and which of the three sources (`--data`, `$ARBITER_DATA`, the cwd walk)
   supplied it.
2. Distinguish an empty-but-present directory. That case is legitimate at
   bootstrap and should stay green.
3. Same family as item 6: the CLI accepts input it cannot honor and reports
   success.

Related: there is no `arbiter init`. See the bootstrap note in `HANDOFF.md`.

## Validator — machine-enforce the prose rules

### 8. Warn on oversized checklist rows
`^oversized-row-warning`

Machine-enforce the protocol 0.4.7 progressive-disclosure rule
(`PROTOCOL.md#tier-2`: rows are summaries; history relocates to a `see:`-linked
tier-3 doc). The rule was added 2026-08-03 after
`tasks/empiricist-multi-repo-2026q3` accreted 57KB of row prose that flooded
continuation sessions. Prose rules drift without a lint.

- Where: `src/core/validate.ts`. Step length is already parseable, so this is a
  per-step length check that warns and names the row's anchor or leading text.
- Warn, never error.
- Keep the threshold generous, around 400 chars or 4 rendered lines. Standing
  rules and PR links legitimately live in rows. The target is paragraph-length
  logs, not firm one-liners.
- Decision record: `docs/v0.4.7-checklist-progressive-disclosure.md`, settled
  point 4, which explicitly deferred enforcement to here.
- Lands together with item 12 (`^sub-tier2-default`), which makes the warning
  actionable.

### 9. Bound the tier-2 `## Summary`
`^summary-bounded`

A task's `## Summary` should observe progressive disclosure: a light, human- and
agent-readable intro to the task's goals and what it builds. Greater detail belongs
in a tier-3 plan. Its job is to tell a reader what the task **is** before they
commit to more.

Requested: consider a text limit, so the Summary stays a lightweight inspection
interface and does not grow into a log. Evidence:
`tasks/empiricist-multi-repo-2026q3`'s Summary is a single ~500-word paragraph that
must be read in full before the checklist makes sense. It grew one honest append at
a time, which is why the ask is a machine-enforced bound and not a style note. This
is the section-level counterpart to item 8.

## Structure — protocol and type docs

### 10. Plan artifacts get their own section, before the checklist
`^plan-artifacts-section`

Top-level plan artifacts (tickets, Figma files, design docs) are the durable links
a reader reaches for repeatedly. They are reference material for the whole task,
not the output of one step.

- Place the section **before** `## Checklist`.
- Fields are optional. Include only what exists. No empty scaffolding.
- Keep it distinct from `## Artifacts`, which trails the checklist and collects
  what the task **produced** (PRs, releases).
- Why the order matters: a reader needs the ticket and the design before the
  checklist can be interpreted. Today those links are buried in Summary prose or in
  a trailing list below a long checklist.

### 11. Checklist rows must carry their links consistently
`^row-links-consistent`

From reading `tasks/empiricist-multi-repo-2026q3`: row 1 is an appropriate length
but omits the PR links row 2 demonstrates, and row 2 carries one linked PR but
omits the next. The operator reports this pattern throughout. **The inconsistency
is the defect, not the links.**

Two preferences to encode:

- Links belong at the row level, visible on the row itself, not only on the tier-3
  doc behind it.
- **Redundancy across tiers is wanted, not tolerated.** A link on the row and again
  on the linked sub-page is the preferred outcome. Tooling must not de-duplicate
  links across tiers.

Consequence for item 8's implementation: relocation of a row's **history** to
tier 3 must not take the row's **identifiers** with it. Load-bearing links stay.

### 12. Make a tier-2 sub-page the default for nearly all tasks
`^sub-tier2-default`

Nearly every task should have its own tier-2 sub-page. It may be simplest to make
that the default rather than an opt-in when a row grows long. Sizing read from
`tasks/empiricist-multi-repo-2026q3`:

| Rows | Verdict |
|---|---|
| 1-4 | appropriate length |
| 5 | edges on too verbose |
| 6-7 | back to the desired length |
| 12 | too long. Break into separate items, or abstract into a sub-tier2 page |
| 16-17 | extend significantly past expected length. These definitely become sub-pages |

Paired renderer affordance:

- Links inside a task are clickable on the highlighted text.
- Highlight of a task shows a clickable finger-pointer icon when a tier-2 sub-page
  exists, so deeper detail is discoverable without a click.

Bound on the fix, recorded verbatim: *"Even though there are a ton of detail docs,
I like this."* Detail-doc proliferation is not the problem. Row length and
discoverability are. Lands with item 8.

### 13. Type docs need task-vs-goal scope guidance
`^goal-scope`

- A **goal** captures a long workstream (3+ weeks) or a personal/professional
  long-running objective.
- Shorter or single-deliverable work is a **task**, optionally parented to a goal,
  or to an umbrella task when it is one facet of a single ask.
- Companion rule from the same session: a task carries exactly one `parent:`, which
  must point at a top-level task or a goal. One nesting level, which matches the
  existing validator rule. Many tasks may share a parent.

Fold this into `types/goal.md` and the create-path notes in the arbiter skill and
around `PROTOCOL.md#slugs`, so agents choose the right container at creation time.
Docs and spec guidance, likely a decision note rather than code.

## Renderer

### 14. Strikethrough means superseded, not done
`^superseded-vs-done-styling`

- Reserve strikethrough for **superseded** rows. It should mean "this is no longer
  the plan," not "this is finished."
- Render **completed** rows in a muted color.

The two states are semantically different and look identical today, so a finished
checklist cannot be read at a glance: "done, shipped" is indistinguishable from
"abandoned, replaced by the row below."

### 15. Relabel the expanded tasks view
`^tier-label`

The renderer labels the expanded tasks view (a click on the Tasks card) "Tier 2".
That view is an expanded **tier-1** view: a longer listing of card entries, not an
item view. Tiers are levels of specificity, not click depth. Tier 2 is one item's
summary with its direct links, artifacts, checklists and checkpoints, per
`PROTOCOL.md#tier-2`.

Relabel it "Tasks" or "Tasks — expanded", and reserve "Tier 2" for single-item
views. Lives in `src/web/server.ts`.

### 16. Show each task's parent association on the tasks view
`^parent-association`

The tasks view should show each task's `parent:` (and ideally `related:`) as a
small goal or parent link on the entry, so affiliation reads at a glance without a
forced umbrella task.

Motivating case: the three Flightpath workstreams (flightpath-ticket-work,
sierra-chat-monitoring, skip-milestone-pal-eligible) are distinct enough to stay
top-level, each with `parent: goals/redfin-flightpath-2026q3`, but the view gives no
cue that they share a goal. The dashboard hue helps; an explicit link is better,
both for human scanning and for an agent that picks an entry point. Complements the
existing color-coding. Renderer only, no protocol change.
